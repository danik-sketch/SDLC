# Хранение данных: JSON с валидацией и атомарной записью

## Контекст и постановка задачи

Приложение должно сохранять и загружать параметры звука (REQ-FUNC-005), хранить встроенные пресеты и, после обсуждения с заказчиком, пользовательские пресеты (REQ-FUNC-012, SDD 0.2). Файл параметров — внешний ввод, он может быть повреждён (REQ-REL-007). Вопрос: в каком формате и где хранить данные?

## Драйверы решения

* Читаемость и возможность обмена файлами между пользователями (BG-4)
* Устойчивость к повреждённым файлам: ошибка не меняет состояние и не роняет программу
* Отсутствие серверов и баз данных (SRS 2.3)
* Простая версия формата для будущих изменений

## Рассмотренные варианты

* JSON (`System.Text.Json`) с `schemaVersion`, валидацией и атомарной записью
* XML
* Бинарный формат
* SQLite

## Итог решения

Выбранный вариант: «JSON с `schemaVersion`, валидацией и атомарной записью», потому что он соответствует SRS и достаточен по возможностям. Пользовательские пресеты хранятся в `%AppData%\RetroSfxLab\user-presets.json`, встроенные — ресурсом сборки.

### Последствия

* Хорошо, потому что повреждённый файл отвергается сообщением, состояние параметров не меняется
* Хорошо, потому что файлы можно отправлять другим пользователям
* Плохо, потому что размер входного файла ограничен 1 МБ и все поля проверяются вручную
* Нейтрально, потому что при обновлении формата нужно поддерживать чтение старых версий

### Подтверждение

Fuzz-тест `tests/json-fuzz.md`: 10 повреждённых файлов, приложение остаётся работоспособным; тест на перезапуск (пользовательский пресет сохраняется); тест на отказ записи (исходный файл цел).

## Плюсы и минусы вариантов

### JSON (`System.Text.Json`) с `schemaVersion`, валидацией и атомарной записью

* Хорошо, потому что требуется SRS и формат читается человеком
* Хорошо, потому что `System.Text.Json` входит в BCL, зависимостей нет
* Хорошо, потому что атомарная запись (временный файл + переименование) не оставляет полуфайлов
* Нейтрально, потому что валидацию диапазонов нужно писать самим

### XML

* Хорошо, потому что есть схемы
* Плохо, потому что многословный, нет выигрыша относительно JSON

### Бинарный формат

* Хорошо, потому что компактный
* Плохо, потому что нечитаем и хуже для обмена и отладки

### SQLite

* Хорошо, потому что транзакции
* Плохо, потому что избыточно для десятка пресетов и лишняя зависимость
